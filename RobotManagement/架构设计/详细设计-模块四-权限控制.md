# 模块四：权限控制 — 详细设计

> 版本：v1.0 | 日期：2026-05-12

---

## 一、概述

权限控制是整个平台的安全基础，其他所有模块的接口都依赖本模块的认证和鉴权结果。

**两套独立的身份体系：**

| 身份 | 使用方 | 认证方式 | 用途 |
|------|--------|----------|------|
| Operator | 运营人员（浏览器） | 用户名 + 密码 → JWT | 访问管理平台 API |
| Robot | 机器人（MQTT 客户端） | APP ID + API Secret | 连接 EMQX Broker |

两套体系互不干扰，本模块重点设计 Operator 体系，Robot 认证详见模块一。

## 二、账号与角色

### 2.1 角色定义

| 角色 | 说明 | 典型操作 |
|------|------|----------|
| `admin` | 租户管理员 | 管理人员账号、管理所有机器人、管理 API 凭证 |
| `operator` | 普通运营员 | 操作被授权的机器人、查看巡检数据、下发任务 |
| `viewer` | 只读观察员 | 查看机器人状态和巡检数据，不可操作 |

### 2.2 权限集合

API Key 级别的细粒度权限，用于控制机器人 API 凭证的操作范围：

| 权限标识 | 说明 |
|----------|------|
| `state:read` | 查看机器人状态和巡检数据 |
| `order:write` | 下发导航任务 |
| `instantAction:write` | 下发即时指令（暂停/继续/取消任务等；安全急停不复用 `stopPause`） |
| `config:write` | 修改机器人配置 |
| `credential:manage` | 管理 API Key/Secret |

### 2.3 双层鉴权模型

运营人员操作机器人时，需同时满足两层校验：

```
请求到达
    → 第一层：Operator 角色校验
    │     viewer 角色：只读接口放行，写操作拒绝
    │     operator 角色：进入第二层
    │     admin 角色：直接放行，跳过第二层（管理所有机器人）
    │
    → 第二层：operator_robot_access 校验（仅 operator 角色）
          该运营人员是否被授权管理目标机器人
          未授权则返回 403
```

`admin` 角色不需要在 `operator_robot_access` 表中有记录，代码层面对 admin 跳过第二层校验。

API Key 权限（`permissions` 字段）是机器人对外开放的能力声明，用于第三方系统集成场景，不用于运营人员的日常操作鉴权。

## 三、登录与 JWT

### 3.1 登录流程

```
POST /api/auth/login
    → 根据 username 查库，获取 operator 记录（含 operator_id）
    → 账号不存在：直接返回 401（不透露原因，防止用户枚举）
    → 检查 Redis auth:lock:{operator_id}，存在则返回 423（账号已锁定）
    → bcrypt 比对密码
    → 失败：Redis auth:fail_count:{operator_id} 自增，达到 5 次写入 auth:lock:{operator_id}，返回 401
    → 成功：清除 auth:fail_count:{operator_id}
    → 检查 password_reset_required，若为 true 返回特殊状态码提示修改密码
    → 生成 Access Token（JWT，含 jti，有效期 8 小时）
    → 生成 Refresh Token（UUID，SHA-256 hash 后存 Redis，有效期 7 天）
    → 通过 Set-Cookie 下发 Refresh Token（HttpOnly Cookie）
    → 响应体仅返回 Access Token 和当前用户信息
```

**Access Token 与 Refresh Token 的职责**

| | Access Token | Refresh Token |
|--|--|--|
| 形式 | JWT（自包含，可本地验证） | 随机 UUID（不透明，需查 Redis） |
| 有效期 | 8 小时（短） | 7 天（长，滑动续期） |
| 用途 | 携带在每个 API 请求的 `Authorization` Header，后端验证签名后直接从 payload 读取身份，无需查库 | 仅用于换取新的 Access Token，不直接访问业务接口 |
| 存储位置 | 客户端内存（不写 localStorage） | httpOnly Cookie（前端 JavaScript 不可读取） |

**为什么需要两个 token：**

Access Token 有效期短（8 小时），过期后用户需要重新登录。如果只有 Access Token，用户每天都要重新输入密码，体验差。Refresh Token 有效期长（7 天），用户无感知地在后台自动换取新的 Access Token，保持登录状态。

两者分离的安全收益：Access Token 即使泄露，8 小时后自动失效；Refresh Token 服务端存 Redis、浏览器侧存 httpOnly Cookie，前端 JavaScript 无法读取，可以随时主动吊销（注销时删除），而 JWT 本身是无状态的，无法主动失效，只能等过期。

**登录失败锁定策略**

- 连续失败 5 次，账号锁定 15 分钟
- 失败计数存 Redis，Key：`auth:fail_count:{operator_id}`，TTL **固定 15 分钟**，到期自动清零，不随每次失败重置（避免持续攻击永远不触发锁定）
- 锁定状态存 Redis，Key：`auth:lock:{operator_id}`，TTL 15 分钟
- 锁定期间任何登录尝试直接拒绝，不再比对密码（防止时序攻击）
- 登录成功后主动清除失败计数
- 失败记录同时写入 `audit_logs`，action = `OPERATOR_LOGIN_FAILED`，便于事后审计

### 3.2 JWT Payload 设计

```json
{
  "jti": "uuid-v4",       // JWT ID，全局唯一，注销时写入 Redis 黑名单用于主动失效
  "sub": "operator_id",   // Subject，标准字段，存运营人员 ID，用于查库获取完整信息
  "tenant_id": "...",     // 租户 ID，每次请求从 token 中直接读取，用于租户隔离过滤
  "role": "admin",        // 角色（admin / operator / viewer），用于第一层角色校验
  "iat": 1715500000,      // Issued At，签发时间戳（Unix 秒）
  "exp": 1715528800       // Expiration，过期时间戳（Unix 秒），8 小时后失效
}
```

不在 JWT 中存放权限列表，权限从数据库实时查询，避免权限变更后 token 未过期导致的不一致。

### 3.3 Token 刷新流程

```
POST /api/auth/refresh
    → 浏览器自动携带 httpOnly Cookie 中的 refresh_token
    → 后端从 Cookie 读取 Refresh Token，不接受请求 Body 中的 refreshToken
    → 校验 Origin / Referer，防止跨站请求伪造
    → 对 token 值做 SHA-256 hash，查 Redis Key：auth:refresh:{hash}
    → 确认存在且未过期
    → 签发新 Access Token
    → Refresh Token 滑动续期（重置 Redis 7 天 TTL，并重新 Set-Cookie）
```

### 3.4 注销流程

```
POST /api/auth/logout
    → 将 Access Token 的 jti（JWT ID）加入 Redis 黑名单，TTL = 剩余有效期
    → 删除 Redis 中的 Refresh Token
    → 清除浏览器 refresh_token Cookie
```

Spring Security Filter 每次验证 JWT 时额外查一次黑名单，命中则拒绝。

### 3.5 Redis Key 设计

| Key | 内容 | TTL |
|-----|------|-----|
| `auth:refresh:{token_hash}` | `{operator_id, token_id}` JSON | 7 天 |
| `auth:blacklist:{jti}` | 固定值 "1" | Access Token 剩余有效期 |
| `auth:fail_count:{operator_id}` | 连续失败次数 | 固定 15 分钟，到期自动清零 |
| `auth:lock:{operator_id}` | 固定值 "1" | 15 分钟 |

Refresh Token 以 SHA-256 hash 作为 Key，Value 存 `operator_id` 和 `token_id`，支持同一账号多端同时登录。注销时从 Cookie 读取当前会话 Refresh Token，计算 token hash 后定位并删除，只影响当前会话。

**Refresh Token Cookie 安全策略**

| 属性 | 策略 |
|------|------|
| Cookie 名称 | `refresh_token` |
| HttpOnly | 必须开启，禁止前端 JavaScript 读取 |
| Secure | 生产环境必须开启，仅 HTTPS 传输 |
| SameSite | 同站部署使用 `Strict`；存在跨子域控制台场景时使用 `Lax` |
| Path | 限制为 `/api/auth`，只在登录、刷新、注销接口携带 |
| CORS | 若前后端跨域，后端只允许可信 Origin，前端 Axios 开启 `withCredentials` |
| CSRF 防护 | `/api/auth/refresh`、`/api/auth/logout` 校验 `Origin` / `Referer` |

## 四、接口设计

### 4.1 认证接口

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| POST | `/api/auth/login` | 登录，获取 token | 公开 |
| POST | `/api/auth/refresh` | 刷新 Access Token | 携带 Refresh Token Cookie |
| POST | `/api/auth/logout` | 注销 | 已登录 |
| GET | `/api/auth/me` | 获取当前登录人信息 | 已登录 |

**使用场景：**
- `login`：用户在登录页输入用户名和密码，成功后前端只保存 Access Token；Refresh Token 由后端写入 httpOnly Cookie
- `refresh`：前端检测到 Access Token 即将过期（或请求返回 401）时，静默调用此接口换取新 Access Token，用户无感知
- `logout`：用户主动点击退出登录，前端调用此接口使服务端 token 失效，同时由后端清除 Refresh Token Cookie
- `me`：前端页面初始化时调用，获取当前登录人的姓名、角色等信息用于页面展示

### 4.2 运营人员管理

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET | `/api/operators` | 查询运营人员列表 | admin |
| POST | `/api/operators` | 创建运营人员 | admin |
| PUT | `/api/operators/{id}` | 修改运营人员信息 | admin |
| PUT | `/api/operators/{id}/password` | 重置密码 | admin 或本人 |
| DELETE | `/api/operators/{id}` | 删除运营人员 | admin |

**使用场景：**
- `GET /operators`：admin 在人员管理页查看租户下所有运营人员列表
- `POST /operators`：admin 新增运营人员账号，系统生成初始密码并设置 `password_reset_required=true`，要求首次登录修改
- `PUT /operators/{id}`：admin 修改运营人员的角色或基本信息（如姓名）
- `PUT /operators/{id}/password`：admin 重置他人密码（如员工忘记密码）；或运营人员本人修改自己的密码
- `DELETE /operators/{id}`：admin 删除离职人员账号，同时其持有的 token 在下次请求时因账号不存在而失效

### 4.3 机器人访问授权

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET | `/api/operators/{id}/robots` | 查询该人员可管理的机器人 | admin 或本人 |
| POST | `/api/operators/{id}/robots` | 授权机器人给运营人员 | admin |
| DELETE | `/api/operators/{id}/robots/{robotId}` | 撤销授权 | admin |

**使用场景：**
- `GET /operators/{id}/robots`：admin 查看某运营人员被授权管理哪些机器人；运营人员本人查看自己有权操作的机器人范围
- `POST /operators/{id}/robots`：admin 将指定机器人的操作权限分配给某运营人员，写入 `operator_robot_access` 表
- `DELETE /operators/{id}/robots/{robotId}`：admin 撤销某运营人员对指定机器人的操作权限，例如人员调岗或机器人转移

### 4.4 API 凭证管理

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET | `/api/robots/{robotId}/credentials` | 查询凭证列表（不返回 secret） | admin 或有该机器人访问权的 operator |
| POST | `/api/robots/{robotId}/credentials` | 创建凭证（Secret 仅此一次返回） | admin |
| DELETE | `/api/robots/{robotId}/credentials/{id}` | 删除凭证 | admin |

**使用场景：**
- `GET /robots/{robotId}/credentials`：查看某台机器人当前有哪些有效的 API Key，用于排查连接问题或审计凭证数量；不返回 Secret，防止泄露
- `POST /robots/{robotId}/credentials`：为机器人创建新的 API Key + Secret，Secret 仅在响应中返回一次，需立即交给硬件团队烧录；常见于机器人首次激活或凭证轮换
- `DELETE /robots/{robotId}/credentials/{id}`：删除失效或泄露的凭证，机器人下次连接 EMQX 时认证失败，强制下线

## 五、Spring Security 配置要点

### 5.1 Filter 链顺序

```
JwtAuthenticationFilter        # 解析 JWT，写入 SecurityContext
    → TenantIsolationFilter    # 校验请求资源的 tenant_id 与 token 中一致
    → RateLimitFilter          # Bucket4j 限流
    → 业务 Controller
```

**JwtAuthenticationFilter**

每个请求进入时首先执行，职责：
1. 从 `Authorization: Bearer <token>` Header 中提取 JWT
2. 验证签名和有效期
3. 查 Redis `auth:blacklist:{jti}`，命中则拒绝（已注销的 token）
4. 解析 `sub`（operator_id）、`tenant_id`、`role` 写入 `SecurityContext`
5. 无 token 或验证失败：返回 401，不继续执行后续 Filter

公开接口（`/api/auth/login`、`/api/auth/refresh`）配置为跳过此 Filter。

**TenantIsolationFilter**

JWT 验证通过后执行，防止运营人员跨租户访问资源：
1. 提取 URL 路径中的资源 ID（如 `/api/robots/{robotId}` 中的 `robotId`）
2. 查库确认该资源的 `tenant_id` 与 token 中的 `tenant_id` 一致
3. 不一致则返回 403，不透露资源是否存在

Service 层查询时强制带 `tenant_id` 条件是主要防线，但依赖开发者每次都写对。若某个接口漏写了 `tenant_id` 过滤，直接用资源 ID 裸查，就可能让 A 租户的运营人员访问到 B 租户的数据。`TenantIsolationFilter` 在 Service 层执行之前独立校验一次资源归属，即使 Service 层存在遗漏，Filter 这一层也会拦截跨租户请求，两者共同保证租户隔离。

**RateLimitFilter**

租户隔离校验通过后执行，基于 Bucket4j + Redis 实现按租户限流：
1. 以 `tenant_id` 为 Key 从 Redis 获取令牌桶
2. 尝试消费一个令牌，成功则放行
3. 令牌不足则返回 429 Too Many Requests，响应 Header 携带 `Retry-After`
4. 不同接口配置不同限流规则（见 2.2 安全设计限流规则）

### 5.2 租户隔离实现

所有涉及资源的接口，在 Service 层查询时强制带上 `tenant_id`：

```java
// 错误示范：直接用 id 查，可能跨租户
robotMapper.selectById(robotId);

// 正确做法：带上当前租户 id
robotMapper.selectOne(
    new LambdaQueryWrapper<Robot>()
        .eq(Robot::getId, robotId)
        .eq(Robot::getTenantId, SecurityUtils.getCurrentTenantId())
);
```

`TenantIsolationFilter` 作为兜底，对 URL 路径中含资源 ID 的请求做二次校验。

### 5.3 密码安全

- 存储：BCrypt，cost factor = 12
- 传输：HTTPS，明文传输到服务端后立即 hash，不在内存中长期保留明文
- 重置：admin 重置后强制用户下次登录修改密码（`operators` 表需增加 `password_reset_required BOOLEAN NOT NULL DEFAULT FALSE` 字段）

### 5.4 WebSocket 订阅鉴权

REST 接口鉴权不能覆盖 STOMP 订阅场景。后端需要在 WebSocket 层做两次校验：

1. `CONNECT` 阶段：从 Header 中提取 `Authorization: Bearer <token>`，复用 JWT 验签、过期时间、黑名单校验逻辑，解析 `tenant_id`、`operator_id`、`role`。
2. `SUBSCRIBE` 阶段：解析订阅路径中的 `robot_id` 或全局 Topic，校验订阅目标属于当前 `tenant_id`，并按角色校验访问权。

订阅权限规则：

| 订阅目标 | admin | operator | viewer |
|----------|-------|----------|--------|
| `/topic/alerts` | 本租户告警 | 本租户告警 | 本租户告警 |
| `/topic/robots/{id}/state` | 本租户任意机器人 | 已授权机器人 | 已授权机器人 |
| `/topic/robots/{id}/position` | 本租户任意机器人 | 已授权机器人 | 已授权机器人 |
| `/topic/robots/{id}/connection` | 本租户任意机器人 | 已授权机器人 | 已授权机器人 |
| `/topic/robots/{id}/order-status` | 本租户任意机器人 | 已授权机器人 | 已授权机器人 |

前端菜单隐藏和按钮禁用只用于减少误操作，不能作为 WebSocket 订阅安全边界。

## 六、审计日志触发点

权限模块需记录以下操作到 `audit_logs`：

| action | 触发时机 |
|--------|----------|
| `OPERATOR_LOGIN` | 登录成功 |
| `OPERATOR_LOGIN_FAILED` | 登录失败（记录 IP，用于暴力破解检测） |
| `OPERATOR_LOGOUT` | 主动注销 |
| `OPERATOR_CREATED` | 创建运营人员 |
| `OPERATOR_DELETED` | 删除运营人员 |
| `OPERATOR_ROLE_CHANGED` | 角色变更 |
| `OPERATOR_PASSWORD_RESET` | 密码重置 |
| `ROBOT_ACCESS_GRANTED` | 授权机器人给运营人员 |
| `ROBOT_ACCESS_REVOKED` | 撤销授权 |
| `CREDENTIAL_CREATED` | 创建 API 凭证 |
| `CREDENTIAL_DELETED` | 删除 API 凭证 |

## 七、已确认决策

| 事项 | 决策 |
|------|------|
| Access Token 有效期 | 8 小时 |
| Refresh Token 有效期 | 7 天，滑动续期 |
| 登录失败锁定 | 连续失败 5 次，锁定 15 分钟 |
| 多端登录 | 允许，每个会话独立 token，互不影响 |
