# 模块三：任务下发 — 详细设计

> 版本：v1.0 | 日期：2026-05-12

---

## 一、概述

任务下发模块负责将运营人员的操作指令通过 VDA5050 v3.0 协议下发给机器人，并跟踪任务执行状态。

**核心职责**
- 构造符合 VDA5050 v3.0 规范的 Order / instantActions 报文，发布到 EMQX
- 记录任务下发历史，支持状态查询和回溯
- 通过解析机器人上报的 state 报文跟踪任务执行进度
- 权限校验：运营人员只能操作被授权的机器人

**两类指令**

| 指令类型 | Topic | 用途 |
|----------|-------|------|
| Order | `uagv/v3/{manufacturer}/{serialNumber}/order` | 导航任务，包含节点序列和边序列 |
| instantActions | `uagv/v3/{manufacturer}/{serialNumber}/instantActions` | 即时指令，立即执行，不进入任务队列 |

---

## 二、VDA5050 报文设计

### 2.1 Order 报文

Order 是导航任务的核心报文，描述机器人需要经过的节点序列和连接节点的边序列。

```json
{
  "headerId": 1,
  "timestamp": "2026-05-12T10:00:00.000Z",
  "version": "3.0.0",
  "manufacturer": "JSYS",
  "serialNumber": "RBT-SN-1001",
  "orderId": "order-uuid",
  "orderUpdateId": 0,
  "nodes": [
    {
      "nodeId": "node-001",
      "sequenceId": 0,
      "released": true,
      "nodePosition": {
        "x": 1.0,
        "y": 2.0,
        "theta": 0.0,
        "mapId": "map-floor1"
      },
      "actions": []
    },
    {
      "nodeId": "node-002",
      "sequenceId": 2,
      "released": true,
      "nodePosition": {
        "x": 5.0,
        "y": 2.0,
        "theta": 1.57,
        "mapId": "map-floor1"
      },
      "actions": [
        {
          "actionType": "pick",
          "actionId": "action-uuid",
          "blockingType": "HARD",
          "actionParameters": [
            { "key": "stationId", "value": "ST-01" }
          ]
        }
      ]
    }
  ],
  "edges": [
    {
      "edgeId": "edge-001",
      "sequenceId": 1,
      "released": true,
      "startNodeId": "node-001",
      "endNodeId": "node-002",
      "maxSpeed": 1.5,
      "actions": []
    }
  ]
}
```

**关键字段说明**

| 字段 | 说明 |
|------|------|
| `orderId` | 任务唯一标识，平台生成 UUID，机器人用于去重 |
| `orderUpdateId` | 任务版本号，从 0 开始递增，用于任务更新（追加节点/边） |
| `nodes[].sequenceId` | 节点序号，偶数（0, 2, 4...），与边的奇数序号交替排列 |
| `edges[].sequenceId` | 边序号，奇数（1, 3, 5...） |
| `released` | 是否释放给机器人执行，false 表示机器人需等待后续 update 才能执行该段 |
| `blockingType` | 动作阻塞类型：HARD（阻塞导航）/ SOFT（不阻塞）/ NONE |

### 2.2 instantActions 报文

即时指令立即执行，不依赖当前任务状态，常用于暂停、继续、取消任务、请求 factsheet 等控制操作。安全急停属于机器人安全状态上报和告警范畴，不在本模块中作为通用远程下发指令；如需远程安全急停，必须单独确认厂商支持的 actionType 或硬件安全链路。

```json
{
  "headerId": 1,
  "timestamp": "2026-05-12T10:00:00.000Z",
  "version": "3.0.0",
  "manufacturer": "JSYS",
  "serialNumber": "RBT-SN-1001",
  "instantActions": [
    {
      "actionType": "stopPause",
      "actionId": "action-uuid",
      "blockingType": "HARD",
      "actionParameters": []
    }
  ]
}
```

**常用即时指令类型**

| actionType | 说明 |
|------------|------|
| `stopPause` | 暂停 / 停止移动，保留当前任务（注意：stop**Pause** = 触发暂停，不等同于安全急停） |
| `startPause` | 继续，恢复暂停前的任务（注意：start**Pause** = 结束暂停，命名来自 VDA5050 规范） |
| `cancelOrder` | 取消当前任务 |
| `factsheetRequest` | 请求机器人上报 factsheet |

### 2.3 headerId 管理

VDA5050 要求同一机器人所有类型报文（Order、instantActions）的 `headerId` 全局单调递增，不区分报文类型。平台使用 Redis 维护每台机器人的统一 headerId 计数器：

```
Key：robot:header:{robot_id}
操作：INCR（原子自增）
TTL：无（永久保留）
```

每次下发任何报文前执行 `INCR`，取返回值作为本次报文的 `headerId`。Order 和 instantActions 共用同一个计数器，保证全局单调递增。

## 三、下发流程

### 3.1 Order 下发流程

```
POST /api/robots/{robotId}/orders
    → 第一层：Operator 角色校验（viewer 拒绝）
    → 第二层：operator_robot_access 校验（operator 角色需有该机器人授权）
    → 查询机器人状态：robots.status = 'active'，否则返回 400
    → 查询机器人在线状态：Redis robot:{id}:online 存在，否则返回 409（机器人离线）
    → 生成 orderId（UUID v4）
    → 从 Redis INCR robot:header:{robot_id} 获取 headerId
    → 构造 VDA5050 Order 报文
    → 发布到 EMQX（QoS 1）
    → MQTT 发布失败：返回 503，不写 orders 表，不写审计日志
    → 写入 orders 表（status = 'pending'）
    → 写审计日志 ORDER_CREATED
    → 返回 orderId 给前端
```

### 3.2 instantActions 下发流程

```
POST /api/robots/{robotId}/instant-actions
    → 第一层：Operator 角色校验（viewer 拒绝）
    → 第二层：operator_robot_access 校验
    → 查询机器人状态：robots.status = 'active'，否则返回 400
    → 查询机器人在线状态：Redis robot:{id}:online 存在，否则返回 409（机器人离线）
    → 生成 actionId（UUID v4）
    → 从 Redis INCR robot:header:{robot_id} 获取 headerId
    → 构造 VDA5050 instantActions 报文
    → 发布到 EMQX（QoS 1）
    → MQTT 发布失败：返回 503，不写审计日志
    → 写审计日志 INSTANT_ACTION_SENT
    → 返回 actionId 给前端
```

> instantActions 不写入 orders 表，仅记录审计日志。

### 3.3 离线机器人处理

下发前检查 Redis `robot:{id}:online`，机器人离线时直接返回 409，不发布 MQTT 消息，不写 orders 记录。

原因：MQTT QoS 1 保证消息至少投递一次，但不保证机器人当前在线。若机器人离线后重新上线，Broker 会将积压消息一次性投递，可能导致机器人执行过期任务。因此在下发前强制检查在线状态，离线时拒绝下发。

## 四、任务状态跟踪

### 4.1 orders 表状态机

```
pending（已下发，等待机器人响应）
    → active（机器人开始执行，state.orderId 匹配）
    → completed（机器人完成任务，nodeStates 为空且 actionStates 全部 FINISHED）
    → failed（任务执行失败，actionStates 中存在 actionStatus = "FAILED" 的动作）
    → cancelled（运营人员主动取消）
```

### 4.2 状态更新触发

任务状态由 state 处理器（模块二）在解析机器人上报的 state 报文时更新，不轮询：

```
state 处理器收到 state 报文
    → 提取 orderId、orderUpdateId、nodeStates、actionStates
    → 若 state.orderId 为空：跳过任务状态更新
    → 查 orders 表：robot_id + order_id 匹配
    → 未找到匹配记录：跳过（非本平台下发的任务）
    → 若 orders.status 为 'completed'、'failed'、'cancelled'：跳过（已终态，不再更新）
    → 若 orders.status = 'pending'：更新为 'active'（机器人已接收并开始执行）
    → 判断任务失败（优先判断）：state.actionStates 中存在 actionStatus = 'FAILED'
        → 满足：更新 orders.status = 'failed'
    → 判断任务完成：state.nodeStates 为空（无剩余待执行节点）
                    且 state.actionStates 中所有 action 均为 FINISHED
        → 满足：更新 orders.status = 'completed'，写 completed_at = now()
```

**说明：**
- `state.orderId` 是机器人当前正在执行的任务 ID，机器人接收到 Order 后才会在 state 中携带该字段
- `nodeStates` 为空表示机器人已到达所有节点，无剩余路径段待执行
- `actionStates` 全部 FINISHED 表示所有动作（如取货、放货）均已完成
- 两个条件同时满足才判定为 completed，避免机器人到达终点但动作未完成时误判
- 本设计不支持分段释放（`released=false`），所有节点和边下发时均设为 `released=true`，因此 `nodeStates` 为空即代表整个任务路径执行完毕

### 4.3 任务取消

```
PUT /api/robots/{robotId}/orders/{orderId}/cancel
    → 权限校验
    → 查 orders 表，确认 status 为 pending 或 active，否则返回 409
    → 更新 orders.status = 'cancelled'（先写库，保证数据一致性）
    → 下发 instantActions cancelOrder 指令（MQTT 发布失败只记日志，不回滚；机器人可能继续执行直到完成或遇到障碍，运营人员可通过暂停/现场安全措施兜底）
    → 写审计日志 ORDER_CANCELLED
```

> 先更新数据库再发 MQTT，避免 MQTT 成功但数据库失败导致的状态不一致。MQTT 发布失败时机器人可能仍在执行，但平台侧已标记取消，运营人员可通过暂停指令或现场安全措施兜底。

## 五、接口设计

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| POST | `/api/robots/{robotId}/orders` | 下发导航任务 | admin / operator（需机器人访问权） |
| GET | `/api/robots/{robotId}/orders` | 查询任务列表（分页） | admin / operator / viewer |
| GET | `/api/robots/{robotId}/orders/{orderId}` | 查询任务详情 | admin / operator / viewer |
| PUT | `/api/robots/{robotId}/orders/{orderId}/cancel` | 取消任务 | admin / operator（需机器人访问权） |
| POST | `/api/robots/{robotId}/instant-actions` | 下发即时指令 | admin / operator（需机器人访问权） |

**接口使用场景：**
- `POST /orders`：运营人员在任务下发页面配置路径节点后提交，平台构造 Order 报文下发给机器人
- `GET /orders`：查看某台机器人的历史任务列表，支持按状态筛选（如只看进行中的任务）
- `GET /orders/{orderId}`：查看单条任务的详细信息，包含完整的 VDA5050 报文内容和当前执行状态
- `PUT /orders/{orderId}/cancel`：运营人员发现任务异常时主动取消，平台同时下发 cancelOrder 即时指令
- `POST /instant-actions`：下发暂停、继续、取消任务等即时控制指令，不经过任务队列，立即生效。安全急停不复用 `stopPause`，需单独设计。

**租户隔离说明：**

orders 表没有 `tenant_id` 字段，租户隔离通过 `robot_id → robots.tenant_id` 关联实现。Service 层查询 orders 时必须先校验 `robotId` 归属当前租户，再查 orders，禁止直接用 `orderId` 裸查：

```java
// 正确做法：先校验 robot 归属，再查 orders
Robot robot = robotMapper.selectOne(
    new LambdaQueryWrapper<Robot>()
        .eq(Robot::getId, robotId)
        .eq(Robot::getTenantId, SecurityUtils.getCurrentTenantId())
);
if (robot == null) throw new ForbiddenException();
// 再查该 robot 下的 orders
```

### 5.1 下发 Order 请求体

```json
{
  "nodes": [
    {
      "nodeId": "node-001",
      "nodePosition": { "x": 1.0, "y": 2.0, "theta": 0.0, "mapId": "map-floor1" },
      "actions": []
    },
    {
      "nodeId": "node-002",
      "nodePosition": { "x": 5.0, "y": 2.0, "theta": 1.57, "mapId": "map-floor1" },
      "actions": [
        {
          "actionType": "pick",
          "blockingType": "HARD",
          "actionParameters": [{ "key": "stationId", "value": "ST-01" }]
        }
      ]
    }
  ],
  "edges": [
    {
      "edgeId": "edge-001",
      "startNodeId": "node-001",
      "endNodeId": "node-002",
      "maxSpeed": 1.5,
      "actions": []
    }
  ]
}
```

前端只需提供业务字段，以下字段由后端自动填充：
- `headerId`、`orderId`、`orderUpdateId`、`timestamp`、`version`、`manufacturer`、`serialNumber`：后端生成
- `nodes[].sequenceId`：后端按数组顺序自动生成，从 0 开始，步长 2（即 0, 2, 4...）
- `edges[].sequenceId`：后端按数组顺序自动生成，从 1 开始，步长 2（即 1, 3, 5...）
- `nodes[].actions[].actionId`：后端为每个动作生成 UUID

### 5.2 下发 instantActions 请求体

```json
{
  "actions": [
    {
      "actionType": "stopPause",
      "blockingType": "HARD",
      "actionParameters": []
    }
  ]
}
```

请求体字段 `actions` 是平台自定义格式，后端负责将其转换为 VDA5050 规范的 `instantActions` 字段名，并补充 `actionId`、`headerId`、`timestamp` 等字段后再发布到 EMQX，不直接透传。

## 六、WebSocket 推送

任务状态变更时，state 处理器更新 orders 表后，通过 WebSocket 推送任务状态变更事件：

```
前端 → SUBSCRIBE /topic/robots/{robot_id}/order-status
后端 → 推送 { orderId, status, updatedAt }
```

前端任务列表页订阅该 Topic，实时感知任务状态变化，无需轮询。

后端推送时按 JWT 中的 `tenant_id` 做隔离，只推送给归属同一租户的前端连接。订阅路径不携带 `tenant_id`，防止越权订阅其他租户机器人的任务状态。

后端必须在 STOMP `SUBSCRIBE` 阶段校验订阅者是否有目标机器人访问权：`admin` 可订阅本租户全部机器人任务状态，`operator` / `viewer` 只能订阅 `operator_robot_access` 中授权的机器人任务状态。

## 七、审计日志触发点

| action | 触发时机 |
|--------|----------|
| `ORDER_CREATED` | 下发导航任务 |
| `ORDER_CANCELLED` | 取消任务 |
| `INSTANT_ACTION_SENT` | 下发即时指令（记录 actionType） |

## 八、已确认决策

| 事项 | 决策 |
|------|------|
| 通信协议 | VDA5050 v3.0 over MQTT |
| 下发 QoS | QoS 1（至少一次投递） |
| 离线下发 | 拒绝，返回 409，不积压消息 |
| headerId 管理 | Redis INCR，按机器人维护独立计数器 |
| instantActions 持久化 | 不写 orders 表，仅记录审计日志 |
| 任务状态更新 | 由 state 处理器事件驱动，不轮询 |
