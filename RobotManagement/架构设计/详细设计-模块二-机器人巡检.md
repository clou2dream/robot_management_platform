# 模块二：机器人巡检 — 详细设计

> 版本：v1.0 | 日期：2026-05-12

---

## 一、概述

机器人巡检模块负责实时采集、存储、展示机器人的运行状态，并在异常时触发告警通知。

**核心职责**
- 订阅机器人通过 VDA5050 v3.0 上报的 MQTT 消息，解析并持久化
- 维护机器人实时状态快照，支持前端秒级感知状态变化
- 检测异常状态，触发告警并通过飞书推送通知
- 记录连接状态变更，支持离线历史回溯

---

## 二、数据上报规范

### 2.1 Topic 与上报频率

| Topic | 方向 | 频率 | 用途 |
|-------|------|------|------|
| `uagv/v3/{manufacturer}/{serialNumber}/state` | 机器人 → 平台 | 1-2Hz | 完整状态（位置、电池、任务、错误等） |
| `uagv/v3/{manufacturer}/{serialNumber}/visualization` | 机器人 → 平台 | 最高 10Hz | 高频位置流，用于实时地图渲染 |
| `uagv/v3/{manufacturer}/{serialNumber}/connection` | 机器人 → 平台 | 事件触发 | 连接状态变更，含 Last Will |
| `uagv/v3/{manufacturer}/{serialNumber}/factsheet` | 机器人 → 平台 | 上线时一次 | 机器人能力描述（静态信息） |

### 2.2 connection Topic 与 Last Will

机器人连接 EMQX 时预设 Last Will 消息：

```json
{
  "headerId": 0,
  "timestamp": "2026-05-12T10:00:00Z",
  "version": "3.0.0",
  "manufacturer": "JSYS",
  "serialNumber": "RBT-SN-1001",
  "connectionState": "CONNECTION_BROKEN"
}
```

- 机器人**主动断开**时发布 `connectionState: "OFFLINE"`
- 机器人**异常掉线**时 EMQX 自动代发 Last Will，`connectionState: "CONNECTION_BROKEN"`
- 机器人**上线**时发布 `connectionState: "ONLINE"`
- 机器人**休眠**时发布 `connectionState: "HIBERNATING"`

后端通过 connection Topic 驱动在线状态管理，不依赖心跳超时轮询。

## 三、数据处理流程

### 3.1 整体数据流

```
机器人 MQTT 上报
    → EMQX Broker 接收
    → 后端 MQTT 订阅服务（Spring Integration MQTT）消费
    → 按 Topic 类型分发到对应处理器
    ├── state 处理器
    │       → 解析 VDA5050 State 报文
    │       → 写入 robot_states（TimescaleDB，异步）
    │       → 更新 Redis robot:{id}:state 快照
    │       → 推送 WebSocket（前端巡检面板）
    │       → 触发告警引擎
    ├── visualization 处理器
    │       → 解析位置数据
    │       → 写入 robot_positions（TimescaleDB，异步）
    │       → 更新 Redis robot:{id}:position 快照
    │       → 推送 WebSocket（前端实时地图）
    ├── connection 处理器
    │       → 解析 connectionState
    │       → 写入 robot_connections（TimescaleDB）
    │       → 更新 Redis robot:{id}:online
    │       → 推送 WebSocket（在线状态变更）
    │       → connectionState=CONNECTION_BROKEN 时触发告警引擎
    └── factsheet 处理器
            → 解析机器人能力描述
            → 更新 robots 表静态信息字段（如有）
```

### 3.2 写入策略

**先写 PostgreSQL，再写 Redis**，保证持久化数据不丢失。Redis 写入失败不影响主流程，下一条消息到来时自然覆盖。

| 数据类型 | 写入方式 | 原因 |
|----------|----------|------|
| state / visualization | 异步批量写入 | 高频写入，避免阻塞消息消费 |
| connection | 同步写入 | 事件频率低，需保证顺序 |
| Redis 快照 | 同步覆盖写 | 实时性要求高 |

## 四、告警引擎

### 4.1 告警触发条件

告警引擎由两个入口触发，分别处理不同来源的异常：

**入口一：state 处理器触发**（每条 state 消息到达后检查）

| 检查项 | 触发条件 | 告警级别 |
|--------|----------|----------|
| 电量 | `batteryState.batteryCharge < 10%` | URGENT |
| 安全急停 | `safetyState.eStop != "NONE"` | CRITICAL |
| 错误列表 | `errors` 数组中存在 `errorLevel = "FATAL"` | FATAL |
| 错误列表 | `errors` 数组中存在 `errorLevel = "WARNING"` | WARNING |

**入口二：connection 处理器触发**（connection 消息到达后检查）

| 检查项 | 触发条件 | 告警级别 |
|--------|----------|----------|
| 连接中断 | `connectionState = "CONNECTION_BROKEN"` | CRITICAL |

> `connectionState = "OFFLINE"` 为机器人主动正常断开，不触发告警。

### 4.2 告警去重

同一机器人同一 `error_type` 的告警，若上一条尚未 `resolved`，不重复创建新告警记录，避免告警风暴。

对于 VDA5050 `errors` 数组中的错误，`error_type` 直接取 `errors[].errorType` 字段。对于 connection 类告警，使用固定值 `error_type = "CONNECTION_BROKEN"` 作为去重 Key。

```
收到告警触发条件
    → 查 alerts 表：robot_id + error_type + resolved_at IS NULL
    → 已存在未解决告警：跳过，不重复写入
    → 不存在：写入新告警记录，触发通知
```

### 4.3 告警自动恢复

| 告警类型 | 自动恢复条件 |
|----------|-------------|
| 电量低 | `batteryCharge >= 20%`（充电后恢复，留 10% 缓冲） |
| 安全急停 | `eStop = "NONE"` |
| 错误 | 对应 `errorType` 从 `errors` 数组中消失 |
| 连接中断 | 机器人重新上线（connection ONLINE） |

自动恢复时更新 `alerts.resolved_at = now()`。

### 4.4 飞书通知

告警写入后，查询 `alert_notification_rules` 表，找到匹配的通知规则（`scope=robot` 或 `scope=tenant`，且 `min_level` ≤ 当前告警级别），向对应 `feishu_webhook` 发送通知。

**告警级别优先级**（从低到高）：`WARNING < URGENT < CRITICAL < FATAL`

飞书消息格式：

```json
{
  "msg_type": "interactive",
  "card": {
    "header": { "title": { "content": "【CRITICAL】机器人安全急停触发", "tag": "plain_text" } },
    "elements": [
      { "tag": "div", "text": { "content": "机器人：RBT-SN-1001\n租户：JSYS\n时间：2026-05-12 10:00:00\n详情：安全急停状态被触发", "tag": "plain_text" } }
    ]
  }
}
```

通知发送失败不影响告警写库，失败记录写入应用运行日志。

## 五、在线状态管理

### 5.1 状态判断逻辑

```
机器人在线状态 = Redis robot:{id}:online 存在
```

- 机器人上线（connection ONLINE）：写入 `robot:{id}:online = 1`，TTL 10s
- 每条 state / visualization 消息到达：刷新 TTL 10s
- 机器人主动下线（connection OFFLINE）：删除 Key
- 机器人异常掉线（connection CONNECTION_BROKEN）：删除 Key
- TTL 自然过期：视为离线（兜底机制，防止 connection 消息丢失）

### 5.2 离线检测

主要依赖 connection Topic 驱动，TTL 过期作为兜底。不使用定时轮询扫描全量机器人，避免无效数据库查询。

## 六、接口设计

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET | `/api/robots/{id}/state` | 获取机器人最新状态（读 Redis） | admin / operator / viewer |
| GET | `/api/robots/{id}/states` | 查询历史状态（分页，读 TimescaleDB） | admin / operator / viewer |
| GET | `/api/robots/{id}/positions` | 查询历史位置轨迹 | admin / operator / viewer |
| GET | `/api/robots/{id}/connections` | 查询连接状态历史 | admin / operator / viewer |
| GET | `/api/alerts` | 查询告警列表（支持按级别、状态、时间过滤） | admin / operator / viewer |
| GET | `/api/alerts/{id}` | 查询告警详情 | admin / operator / viewer |
| PUT | `/api/alerts/{id}/resolve` | 手动标记告警已解决 | admin / operator |
| GET | `/api/robots/{id}/alerts` | 查询指定机器人的告警列表 | admin / operator / viewer |
| GET | `/api/alert-rules` | 查询告警通知规则列表 | admin |
| POST | `/api/alert-rules` | 创建告警通知规则 | admin |
| DELETE | `/api/alert-rules/{id}` | 删除告警通知规则 | admin |

**接口使用场景：**
- `GET /robots/{id}/state`：前端巡检面板初始化时拉取最新状态，后续通过 WebSocket 实时更新
- `GET /robots/{id}/states`：查看机器人历史运行数据，支持时间范围筛选
- `GET /robots/{id}/positions`：回放机器人历史轨迹，在地图上渲染路径
- `GET /alerts`：告警中心页面，展示全租户告警列表，支持筛选未解决告警
- `PUT /alerts/{id}/resolve`：运营人员确认处理完毕后手动关闭告警
- `POST /api/alert-rules`：admin 配置飞书 webhook，指定哪些级别的告警需要推送

## 七、WebSocket 推送设计

前端建立 WebSocket 连接后，订阅感兴趣的机器人：

```
前端 → SUBSCRIBE /topic/robots/{robot_id}/state
前端 → SUBSCRIBE /topic/robots/{robot_id}/position
前端 → SUBSCRIBE /topic/robots/{robot_id}/connection
前端 → SUBSCRIBE /topic/alerts
```

后端收到 MQTT 消息处理完成后，按 `robot_id` 精准推送到订阅该机器人的前端连接，不广播给其他租户。告警推送时后端根据 JWT 中的 `tenant_id` 做隔离，只推送给同租户的连接，前端订阅路径不携带 tenant_id，防止越权订阅其他租户的告警。

**订阅鉴权要求**

后端必须在 STOMP `CONNECT` 阶段校验 JWT，并在每次 `SUBSCRIBE` 阶段校验订阅目标资源归属：

- `admin` 可订阅本租户全部机器人 Topic
- `operator` / `viewer` 只能订阅 `operator_robot_access` 中授权的机器人 Topic
- 告警 Topic `/topic/alerts` 仅推送当前 JWT 所属租户的数据
- 前端隐藏菜单和按钮只作为体验优化，不能作为 WebSocket 订阅鉴权依据

推送频率控制：`visualization` 数据最高 10Hz，前端地图渲染按需降采样，避免渲染压力过大。

## 九、已确认决策

| 事项 | 决策 |
|------|------|
| 通信协议 | VDA5050 v3.0 over MQTT |
| state 上报频率 | 1-2Hz |
| visualization 上报频率 | 最高 10Hz |
| 巡检数据保留 | robot_states / robot_connections：90 天；robot_positions：24 小时 |
| 在线状态检测 | connection Topic 驱动 + Redis TTL 兜底，不轮询 |
| 告警去重 | 同机器人同 errorType 未解决告警不重复创建 |
| 告警通知渠道 | 飞书 Webhook |
