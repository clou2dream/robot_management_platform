# 机器人运营管理平台 — 项目立项汇报

> 汇报日期：2026-05-13

---

## 一、项目背景

建设一套**机器人运营管理平台**，实现对公司全部机器人设备的统一管理，达成以下目标：

- 故障自动感知，告警通知到人，响应时间从小时级压缩到分钟级
- 任务远程下发，操作全程留痕，每一条指令可追溯到具体人员
- 权限精细管控，每位运营人员只能操作被授权的机器人
- 标准化接入，新机器人上线无需人工录入，自动完成鉴权、注册激活

---

## 三、核心功能

| 模块 | 解决的问题 | 具体能力 |
|------|-----------|---------|
| **机器人授权** | 设备无管理、无授权 | 机器人首次上线自动注册激活；一次授权永久有效，断网也能正常工作；支持远程吊销，下次联网立即生效 |
| **实时巡检** | 故障发现滞后、状态不透明 | 实时展示每台机器人的位置、电量、运行状态；地图可视化；异常自动触发告警通知 |
| **任务下发** | 操作不规范、无记录 | 运营人员在平台上配置路径、下发导航任务；支持暂停、继续、取消任务等即时指令；安全急停作为机器人状态和告警展示；所有操作记录可查 |
| **权限管理** | 权限边界不清、误操作风险 | 按角色（管理员/运营员/只读）控制操作范围；每位运营人员只能操作被授权的机器人；多客户数据完全隔离 |

## 四、技术方案

### 4.1 整体架构

系统分为四层：前端操作界面、后端服务、消息中间件（EMQX）、数据存储。

```
前端（React）
    ↕ HTTPS / WebSocket
后端（Spring Boot）
    ↕ SQL          ↕ Redis          ↕ MQTT
PostgreSQL       Redis            EMQX Broker
+TimescaleDB    （缓存/限流）      （机器人通信）
                                       ↕ MQTT
                                   机器人设备
```

- **前端**：React 18 + TypeScript + Ant Design 5，Konva.js 渲染实时地图，STOMP over WebSocket 接收实时推送
- **后端**：Java Spring Boot 3，Spring Security 做认证鉴权，MyBatis-Plus 做数据访问，Bucket4j + Redis 做接口限流
- **数据库**：PostgreSQL 16 存关系数据，TimescaleDB 扩展处理时序数据（机器人状态、位置、连接历史），Redis 做缓存和在线状态管理
- **消息中间件**：EMQX（工业级 MQTT Broker），机器人通过 MQTT 上报状态、接收指令

### 4.2 机器人通信协议

采用 **VDA5050 v3.0**（AGV/AMR 国际标准协议），主流机器人厂商均支持，不绑定特定厂商。

机器人通过 MQTT 上报四类消息：

| Topic | 频率 | 用途 |
|-------|------|------|
| `.../state` | 1-2Hz | 完整状态（位置、电量、任务、错误） |
| `.../visualization` | 最高 10Hz | 高频位置流，用于实时地图渲染 |
| `.../connection` | 事件触发 | 上线/下线/异常掉线（Last Will） |
| `.../factsheet` | 上线时一次 | 机器人能力描述 |

平台通过 `.../order` 和 `.../instantActions` Topic 下发导航任务和即时指令。

### 4.3 机器人授权机制

采用**配额激活**模式，机器人无需平台预录入：

1. 硬件团队出厂时将 APP ID + SN 烧录到机器人本地
2. 机器人首次上线，用 APP ID + SN 连接 EMQX，后端自动完成注册
3. 后端生成 API Key + API Secret，通过 MQTT 下发给机器人
4. 机器人持久化存储凭证，后续断网重连均使用 API Key + API Secret，不依赖平台

凭证一旦泄露可立即吊销，下次联网时 EMQX 认证拒绝，不影响其他设备。

### 4.4 认证与权限

- **运营人员登录**：用户名 + 密码，JWT 双 Token 机制（Access Token 8小时 + Refresh Token 7天滑动续期）
- **Access Token** 存前端内存（不写 localStorage，防 XSS 窃取），Refresh Token 存 httpOnly Cookie
- **RBAC 权限模型**：admin（全权）/ operator（操作被授权机器人）/ viewer（只读）
- **资源级授权**：operator 只能操作 `operator_robot_access` 表中被授权的机器人，后端鉴权兜底

### 4.5 实时推送

后端订阅 EMQX 消息后，通过 Spring WebSocket + STOMP 推送前端：

- 机器人位置（最高 10Hz）→ 前端直接操作 Konva Canvas，不走 React 状态，避免重渲染开销
- 机器人状态变更 → 更新巡检面板状态卡片
- 新告警 → 导航栏红点 + CRITICAL/FATAL 级别弹出全局通知
- 任务状态变更 → 任务列表实时刷新

推送按 `tenant_id` 隔离，不同租户数据不互通。

### 4.6 数据存储策略

| 数据类型 | 存储位置 | 保留周期 |
|----------|----------|----------|
| 机器人状态历史 | TimescaleDB（超表，自动分块） | 90 天 |
| 高频位置流 | TimescaleDB | 24 小时 |
| 连接状态历史 | TimescaleDB | 90 天 |
| 操作审计日志 | PostgreSQL（TimescaleDB 超表） | 90 天 |
| 应用运行日志 | 阿里云 SLS | 30 天 |
| 机器人实时状态快照 | Redis（覆盖写） | 无过期 |
| 机器人在线状态 | Redis（TTL 10s，消息刷新） | 自动过期 |

### 4.7 安全设计

- 所有外部通信强制加密（HTTPS + MQTT/TLS），数据传输不可窃听
- 数据库、Redis 不暴露公网，仅内网访问
- 接口限流（Bucket4j + Redis，按租户隔离）：任务下发 10次/秒，即时指令 20次/秒，普通查询 100次/秒
- 操作日志全量记录，保留 90 天，满足合规审计要求
- 多租户数据隔离：所有业务表携带 `tenant_id`，查询层强制过滤，不同租户数据物理共存但逻辑隔离

## 六、实施计划

采用分阶段交付，优先上线核心功能，快速产生价值。

### 第一阶段：MVP 上线（12个工作日）

交付内容：机器人自动注册激活、实时巡检地图、任务远程下发、平台内告警通知

```
第1-3天    服务器部署（Docker Compose）+ 登录认证（JWT）
第4-6天    机器人授权激活（EMQX 认证回调）+ 实时巡检（MQTT 订阅 + WebSocket 推送）
第7-9天    告警引擎 + 任务下发（VDA5050 Order/instantActions）
第10-12天  前端集成联调 + 生产上线
```

### 第二阶段：功能完善（约21个工作日，MVP 后续迭代）

- 告警中心页面（历史告警查询、统计分析）
- 飞书告警通知
- 人员管理页面（运营人员账号管理、权限分配）
- 历史轨迹回放（机器人行驶路径回溯）
- 机器人详情页（历史状态、连接记录、凭证管理）
- 系统设置（APP ID 管理、告警通知规则配置）
